# TFT_eSPI_ESP8266: versão exclusiva ESP8266 + ST7789

Data: 2026-10-06
Branch: `refactor/esp8266-st7789-only`
Base: fork de `Bodmer/TFT_eSPI` v2.5.44

## Objetivo

Transformar o fork em uma biblioteca própria, leve e legível, que suporta **somente**
ESP8266 + controlador ST7789 via SPI. Não haverá mais sincronização com o upstream,
então a limpeza pode ser agressiva.

**Sucesso:**

1. Os 14 exemplos curados compilam com `pio ci` para `nodemcuv2`, localmente e no CI.
2. No hardware alvo, `Read_User_Setup`, `TFT_graphicstest_PDQ`, um exemplo de Sprite
   e um de Smooth font rodam com saída visual correta.
3. Sketches existentes que usam `#include <TFT_eSPI.h>` e a classe `TFT_eSPI` compilam
   sem alteração, exceto os que usam touch ou DMA.

## Hardware alvo

| Item | Valor |
|---|---|
| Controlador | ST7789V |
| Resolução | 240 × 240 |
| Cor | RGB565 / 16 bits |
| Interface | SPI, Mode 3, ~40 MHz |
| MOSI | GPIO13 |
| SCK | GPIO14 |
| DC | GPIO0 |
| RESET | GPIO2 |
| Backlight | GPIO5, ativo em LOW |
| CS | ligado permanentemente ao GND |
| MISO | não conectado (display só escreve) |

## 2. Limpeza do core

### Passo 1: `unifdef`

Rodar `/usr/bin/unifdef` em `TFT_eSPI.h`, `TFT_eSPI.cpp`, `Processors/TFT_eSPI_ESP8266.{h,c}`,
`Extensions/Sprite.{h,cpp}` e `Extensions/Smooth_font.{h,cpp}`.

Símbolos definidos (`-D`):

```
ARDUINO_ARCH_ESP8266  ESP8266  ST7789_DRIVER
```

Símbolos indefinidos (`-U`):

```
ESP32 CONFIG_IDF_TARGET_ESP32S3 CONFIG_IDF_TARGET_ESP32C3 CONFIG_IDF_TARGET_ESP32C6
CONFIG_SPIRAM_SUPPORT ARDUINO_ARCH_RP2040 ARDUINO_ARCH_MBED RP2040_PIO_INTERFACE
RP2040_PIO_SPI STM32 _VARIANT_ARDUINO_STM32_ __AVR__ GENERIC_PROCESSOR M5STACK
TFT_PARALLEL_8_BIT TFT_PARALLEL_16_BIT ESP32_PARALLEL TFT_SDA_READ SPI_18BIT_DRIVER
RPI_DISPLAY_TYPE RPI_WRITE_STROBE TFT_WR TFT_RD TOUCH_CS CONFIG_TFT_eSPI_ESPIDF
ST7789_2_DRIVER ILI9341_DRIVER ILI9341_2_DRIVER ILI9342_DRIVER ST7735_DRIVER
ILI9163_DRIVER S6D02A1_DRIVER ST7796_DRIVER ILI9486_DRIVER ILI9481_DRIVER
ILI9488_DRIVER HX8357B_DRIVER HX8357C_DRIVER HX8357D_DRIVER R61581_DRIVER
RM68120_DRIVER RM68140_DRIVER SSD1351_DRIVER SSD1963_DRIVER GC9A01_DRIVER
ILI9225_DRIVER
```

Antes de rodar, conferir no código se há algum outro `*_DRIVER` além dos listados
(`grep -o '[A-Z0-9_]*_DRIVER'`) e incluí-lo no `-U`.

Estes símbolos **não** passam pelo `unifdef`, porque continuam sendo opções reais do usuário:
`LOAD_*`, `SMOOTH_FONT`, `FONT_FS_AVAILABLE`, `TFT_SPI_OVERLAP`, `SUPPORT_TRANSACTIONS`,
`TFT_BL`, `TFT_BACKLIGHT_ON`, `TFT_CS`, `TFT_DC`, `TFT_RST`, `TFT_MISO`, `SPI_*FREQUENCY`,
`TFT_SPI_MODE`, `TFT_INVERSION_*`, `TFT_RGB_ORDER`, `CGRAM_OFFSET`, `TFT_WIDTH`, `TFT_HEIGHT`,
`USER_SETUP_LOADED`, `DISABLE_ALL_LIBRARY_WARNINGS`. O `TFT_DRIVER` também fica: ele é o ID
numérico do driver usado pelo `Read_User_Setup`, não um seletor de driver.

O comando exato vai no corpo da mensagem de commit. Não será criado um script para ele.

### Passo 2: incorporar o processador

- Substituir `#include "Processors/TFT_eSPI_ESP8266.h"` em `TFT_eSPI.h` pelo conteúdo do arquivo.
- Substituir `#include "Processors/TFT_eSPI_ESP8266.c"` em `TFT_eSPI.cpp` pelo conteúdo do arquivo.
- Remover os `#include` dos outros processadores que o `unifdef` não tiver eliminado.
- Apagar `Processors/`.

### Passo 3: revisão manual

- Remover a seção da API de DMA do header e da implementação (`initDMA`, `deInitDMA`,
  `pushImageDMA`, `pushPixelsDMA`, `dmaWait`, `dmaBusy` e afins). O ESP8266 não tem DMA,
  então são stubs mortos.
- Remover comentários que falam de plataformas removidas ("ESP32 only", "RP2040", "STM32", "parallel").
- Remover o aviso de compilação "processor not supported".
- Simplificar `User_Setup_Select.h` para:
  `#ifndef USER_SETUP_LOADED` → `#include <User_Setup.h>` → `#endif`.
- Reescrever `User_Setup.h` (seção 3).
- Atualizar `keywords.txt`, retirando touch, DMA e Button.

### Passo 4: `readPixel` sem MISO

Quando o display não tem MISO, a leitura de pixel retorna lixo. Esse valor é usado no
anti-aliasing quando o chamador não passa cor de fundo (`TFT_eSPI.cpp:3961`, `:4527`, `:4565`).

No início de `TFT_eSPI::readPixel`:

```cpp
if (TFT_MISO < 0) return 0; // No MISO wired: display is write-only, assume black
```

A checagem é em tempo de execução contra uma constante, para funcionar mesmo quando
`TFT_MISO` for definido como `static const` (o `D6` do core ESP8266 não pode ser usado em `#if`).
O compilador elimina o ramo morto.

`readRect` e `readRectRGB` não mudam. O README documenta que, sem MISO, eles não funcionam.

### API pública resultante

Fica igual à do upstream, menos touch (`getTouch`, `calibrateTouch`, `setTouch`,
`getTouchRaw`, `getTouchRawZ`, `convertRawXY`), a classe `TFT_eSPI_Button` e a API de DMA.

## 3. Configuração, exemplos e verificação

### `User_Setup.h` padrão

```c
#define USER_SETUP_INFO "TFT_eSPI_ESP8266 default"

#define ST7789_DRIVER
#define TFT_WIDTH  240
#define TFT_HEIGHT 240

#define TFT_MOSI 13
#define TFT_SCLK 14
#define TFT_DC    0
#define TFT_RST   2
#define TFT_BL    5
#define TFT_BACKLIGHT_ON LOW
// TFT_CS not defined: CS tied to GND
// TFT_MISO not defined: display is write-only

#define SPI_FREQUENCY 40000000
// TFT_SPI_MODE defaults to SPI_MODE3 for ST7789

// Calibration knobs, confirm on hardware with Colour_Test
// #define TFT_RGB_ORDER TFT_BGR
// #define TFT_INVERSION_ON

#define LOAD_GLCD
#define LOAD_FONT2
#define LOAD_FONT4
#define LOAD_FONT6
#define LOAD_FONT7
#define LOAD_FONT8
#define LOAD_GFXFF
#define SMOOTH_FONT
```

O arquivo mantém comentários curtos explicando cada opção que continua válida.
Comentários sobre opções removidas saem.

Observação de hardware: GPIO0 (DC) e GPIO2 (RST) são pinos de boot do ESP8266.
O README avisa que eles precisam estar em HIGH durante o boot. Isso já funciona no board alvo.

### Verificação

**Baseline**, antes de qualquer remoção de código: compilar os 14 exemplos contra a lib
original com o `User_Setup.h` alvo. Os exemplos já ficam movidos para `examples/<Nome>/`,
porque o Make não lida com espaços nos caminhos. Falhas aqui são do exemplo, não da
limpeza, e devem ser registradas.

**`Makefile`** (GNU Make 3.81 compatível, sem `platformio.ini`):

- `make build` (padrão) compila todos os `examples/*/` em paralelo (`-j` = número de CPUs).
  Cada exemplo roda
  `pio ci --lib=. --board=nodemcuv2 -O "lib_deps=bitbank2/PNGdec" -O "board_build.filesystem=littlefs" --build-dir .build/<Nome> --keep-build-dir examples/<Nome>`.
- Um carimbo `.build/<Nome>/.ok` depende dos fontes da lib e dos `.ino` do exemplo.
  Se nada mudou, o exemplo é pulado.
- O output vai para `.build/<Nome>.log`, e o terminal mostra só `OK <Nome>` ou `FAIL <Nome>`
  com a cauda do log. Qualquer falha faz o `make` sair com código diferente de zero.
- Também há os alvos `build-<Nome>`, `upload EX=<Nome> [PORT=]`, `uploadfs EX=<Nome> [PORT=]`,
  `monitor [PORT=]`, `clean` e `help`.
- `.build/` entra no `.gitignore`.

**`.github/workflows/build.yml`:** em `push` e `pull_request`, faz `actions/setup-python`,
`pip install platformio` e roda `make build`.

**Hardware**, feito pelo usuário no fim:

1. `Read_User_Setup`: o Serial mostra ST7789, 240×240, os pinos e 40 MHz.
2. `Colour_Test`: as cores estão corretas. Se não, ajustar `TFT_RGB_ORDER` e `TFT_INVERSION_ON` no `User_Setup.h`.
3. `TFT_graphicstest_PDQ` roda sem travar.
4. Um exemplo de Sprite e `Font_Demo_1_Array` renderizam corretamente.
